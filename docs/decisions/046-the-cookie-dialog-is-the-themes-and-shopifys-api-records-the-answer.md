# 046. The cookie dialog is the theme's own native dialog; Shopify's Customer Privacy API decides who is asked and records the answer

Status: accepted (supersedes [decision 030](030-cookie-consent-is-shopifys-banner-and-the-theme-respects-it.md) where it says the theme builds no dialog; the rest of 030 stands)
Area: privacy | consent | accessibility | performance
Code: `snippets/consent-dialog.liquid`, `assets/consent.js`, `layout/theme.liquid`, `sections/footer.liquid` (`.consent-open`), `config/settings_schema.json` (`consent_dialog`), `locales/*.json` (`consent`), `scripts/test-consent.mjs`

## Context

[Decision 030](030-cookie-consent-is-shopifys-banner-and-the-theme-respects-it.md) kept Shopify's own banner because nothing documented a theme replacing or restyling it, and left out a reopen control for the same reason. The owner wants the banner to be part of the theme: the same look as the rest of the store, a native `<dialog>`, small and fast, and good to use (2026-11-18). Shopify's documentation (read 2026-11-18, through search and a page fetch, not on a live store) says:

- the Customer Privacy API is loaded with `Shopify.loadFeatures([{ name: 'consent-tracking-api', version: '1.0' }], callback)` and `Shopify.customerPrivacy` exists after a callback without an error;
- `shouldShowBanner()` says whether the visitor is in a region configured to show the banner, and **not** whether they already answered; `currentVisitorConsent()` returns `{ marketing, analytics, preferences, sale_of_data }` with `'yes'`, `'no'` or `''`;
- `setTrackingConsent({ analytics, marketing, preferences, sale_of_data }, callback)` takes booleans, and nothing extra is listed for an Online Store theme; recording consent must follow a real interaction, never happen automatically;
- the page says nothing about running a custom banner instead of Shopify's; the help article says a third-party banner must use the same consent regions and that Shopify's banner can be removed under Settings > Customer privacy > Cookie banner "where available". How to turn it off when a theme has its own is not documented;
- reopening preferences for a custom banner is left to the theme (`showPreferences()` is documented only for Shopify's banner).

## Decision

- **The theme ships a cookie dialog, off by default**, behind the setting **"Show the theme's cookie dialog"** (`consent_dialog`). Off by default because Shopify's banner is on by default for regions that need it and two would stack; the setting's help text says to remove Shopify's first.
- **Shopify decides who is asked and records the answer; the theme draws the question.** `assets/consent.js` loads the API if needed, shows the dialog only when `shouldShowBanner()` is true **and** `currentVisitorConsent()` has no answer yet, and records with `setTrackingConsent()` after a click. The existing Consent Mode code in `assets/tracking.js` keeps working unchanged: Shopify fires `visitorConsentCollected` when the answer is recorded.
- **A native, modal `<dialog>`: the first ask needs a decision before the page is used** (the owner's rule, 2026-11-18). It opens over a scrim (`--color-scrim`), centered on a wide screen and 16px from the bottom of a phone, with the page behind inert, no page scroll, focus starting on the title and staying inside, and Escape not dismissing it. It is not a cookie wall: Reject all is as easy as Accept all, so nobody is made to accept to go on. It shows by itself, on any page, as soon as the browser is idle and the API says this visitor must be asked and has not answered. Named by its title; first in the DOM after the skip link.
- **The country and language selects are the first thing in the card, above the title.** A visitor should check and correct where they are before reading anything else; the text below them then changes in place when they change the selection, and nothing they are looking at moves. The title is still the `autofocus` target (the first focusable element is the country select, and without `autofocus` the browser's own focusing ran after ours and won), so a screen reader reads the question first.
- **The card is anchored 12% from the top, never centered vertically, and never a bottom sheet.** Its height changes (the language select appears for some countries, Swedish and French words are longer than English, Preferences opens), and a card centered or pinned to the bottom moves its title whenever that happens: the first version did, which showed as a jump when changing language. Anchored from the top it only grows downwards, so the title stays where the visitor is reading. `scripts/test-consent.mjs` adds filler to the card and checks the top and the title do not move.
- **Two choices of equal weight:** "Accept all" and "Reject all" are the same size, weight and look (both the `.button` style, 44px tall or more). "Preferences" folds out a native `<details>` (while it is open, Accept all and Reject all are hidden and "Save choices" is the only primary button in view, so there is one obvious action at a time; closing it brings the two answers back) with Essential (on, locked), Analytics, Marketing and Preferences, each with a one-line note, and "Save choices". `sale_of_data` follows the Marketing choice.
- **Nothing is recorded without a click.** Closing the first ask without answering is not possible (there is no close button then). When it is reopened there is one, and Escape closes it without recording.
- **On a store with more than one country or language, the first ask also confirms the region, in the same dialog.** A visitor who is asked for consent sees the market Shopify resolved for them in two labelled native selects, Country/region and Language (the language select only when the country has more than one). They are always visible, with no heading and no folded summary: a summary line that repeated the selects' values ("Canada (USD) · Français") said nothing the selects do not, and hiding a choice behind a click is a worse default when the point is to confirm it in one action. **Accept all and Reject all each confirm the consent and the region shown with it:** when nothing was changed they only record consent; when the country or language was changed they record consent first and then post Shopify's localization form (`/localization`, with this page as `return_to`), so one click does both. The theme guesses no location and redirects nowhere ([decision 031](031-no-location-prompt-yet-shopify-resolves-the-buyers-country.md) stands: Shopify resolves the market, the dialog only lets the visitor confirm or correct it). A store with a single country and language shows no region row. With more than 12 countries the select holds only the current one and takes the full list from the footer selector the first time it is used (the list is about 240 countries on a store with a Rest of world market and is never rendered in every page).
- **The words are Shopify's cookie banner copy, with the theme's strings as the fallback.** On a real store host the dialog asks the Storefront API (`consentManagement.banner`, the query Shopify's own banner script sends) for its title, text, privacy link, button labels and the category names and descriptions, already translated for the language asked for and edited by the merchant in Settings > Customer privacy > Cookie banner. The public Storefront access token is the one in `script#shopify-features` on every page. Anything Shopify does not return keeps the `consent.*` strings of the theme. The buttons use the preferences panel's wording ("Accept all", "Decline all", "Save my choices"), because the dialog always offers the categories.
- **The paragraph is the theme's, short on purpose, and names no one.** Shopify's banner text ("We and our partners, including Shopify, use cookies and other technologies to personalize your experience, show you ads, and perform analytics, and we will not use cookies or other technologies for these purposes unless you accept them. Learn more in our Privacy Policy") is long and names Shopify, and it is not editable by the theme, so the dialog keeps the theme's `consent.body` (translated in every locale) and takes only the title, the Save and Close labels, the privacy-link text and URL, and the category names and descriptions from Shopify. The two answer buttons are the theme's too, and short on purpose: "Accept" and "Decline" (Shopify's are "Accept all" and "Decline all"; in Swedish "Godkänn" and "Avvisa", not "Godkänn alla" and "Avvisa alla"), translated in every locale. They sit side by side, so there is nothing for "all" to be set against. The merchant owns the wording of the paragraph, in the locale files; check it says what your cookies do.
- **Country and language are preselected from what Shopify detects.** The dialog reads `/browsing_context_suggestions.json?country[enabled]=true&language[enabled]=true` (undocumented, so every part of the answer is optional) and preselects the suggested country when it is one of the select's options; Accept all or Reject all then switch the market if it differs from the page's. This reverses [decision 031](031-no-location-prompt-yet-shopify-resolves-the-buyers-country.md)'s "do not build on the endpoint", at the owner's request (2026-11-18); nothing redirects and nothing applies until the visitor answers.
- **A secondary "Language" select appears only when the chosen country has more than one language.** The languages of every country come from the documented Storefront `localization { availableCountries { availableLanguages } }` in the same request as the copy. They are preselected from the suggestion's language, then the browser's languages (exact, then the primary subtag), then what was chosen, then the page's language, then the first. Options are the languages' own names (`endonymName`). Picking another country or language rebuilds the select and re-fetches the copy, so **the dialog speaks the language being chosen** (and its `lang` follows). A country with one language hides the select, which is then not posted.
- **The whole dialog speaks the language that is selected, never a mix.** Shopify's copy comes translated from the Storefront API, but the theme's own words (the Country/region and Language labels, the Preferences row, and the text and buttons when Shopify's copy is not available) are Liquid strings, and Liquid can only translate into the language of the request. So `npm run docs` writes one small file per language, `assets/consent-strings-<code>.json` (about 1 KB, generated from `locales/*.json`; `npm run check` fails when one is stale or missing). `assets/consent.js` fetches only the one it needs when the visitor picks a language other than the page's, applies it, and puts the page's own words back when they pick the page's language again; Shopify's copy is applied over it. The dialog's `lang` and `dir` follow the chosen language, and the country names follow it too (the Storefront API returns them translated). The first version applied only Shopify's copy, so a visitor who picked Swedish saw Swedish text under English labels. Rejected: one file with every language (60 KB for a single language) and fetching the localized page to read its strings (the URL of another market's language is not known from the page).
- **None of this runs on the dev server.** Through `npm run dev` (a loopback host) the Storefront API answers `400 "Online Store channel is locked."` (the CLI does not carry the store password into API calls), and that one failed request makes the CLI drop its session, so every later page redirects to `/password`. The suggestion endpoint answers 401 there (harmless). So on `127.0.0.1` and `localhost` the dialog skips both and shows the theme's own words and the page's market; a test opts back in with `window.singiConsentLive`. Review the Shopify copy and the language select on the store's preview URL, not on the dev server.
- **Later changes are separate and focused on one task.** The footer "Cookie settings" button reopens the consent part only (no region), and the footer country and language selector stays the way to change the region. The region is shown only while a consent answer is asked for: a visitor in a region that needs no consent is not interrupted (no prompt), as in 031.
- **Reopen from the footer:** a "Cookie settings" button (`.consent-open`) appears once the API is ready and reopens the dialog with the current choices and focus on its title.
- **No JavaScript, no dialog, nothing non-essential runs:** without the API nothing is consented to, which is the safe state. The dialog and the footer button stay hidden when the API cannot load.
- **The text is the theme's `consent` strings**, translated in all 62 locales (machine-translated, native review needed). It is a neutral description, not legal copy; a merchant edits it under Online Store > Languages > Edit default theme content, or per language in Translate & Adapt, and links the privacy policy automatically when one exists.
- **Cost:** `assets/consent.js` is 14,505 bytes source and 4,083 brotli (about 1,050 of it the dialog; the rest the region row, the lazy country list, the modal handling, the preview, Shopify's copy, the suggestion and the language select), loaded only when the setting is on, on every page, `type="module"`, started on idle. Its own raw budget is 14,600 (the default is 6,000) and the total JavaScript budget moved from 23,650 to 27,750 (measured 27,705).

## Why

- **One look, one set of controls:** a banner in the theme's tokens, radius and type, on a native element, instead of a second visual language.
- **Platform logic stays the platform's:** which visitors must be asked (regions), what a "yes" allows and the storage of the answer remain Shopify's, so the theme carries no legal rules and the checkout sees the same consent.
- **Equal weight and no pre-ticked boxes** are the points regulators and Shopify's own guidance stress: a reject as easy as an accept, and nothing recorded until the visitor acts.
- **A required, honest choice** over a polite hint: a question that matters (consent, and the region you will be shown prices in) is asked once, plainly, with equal answers, and the page is not usable until it is answered. The native modal gives the focus trap, the inert background and the scrim for free.

## Alternatives rejected

| Alternative | Why not |
| --- | --- |
| Keep Shopify's banner only ([decision 030](030-cookie-consent-is-shopifys-banner-and-the-theme-respects-it.md)) | The owner wants it in the theme's look and a reopen control; Shopify documents neither a restyle nor a reopen for a theme. |
| A non-modal card at the bottom of the page (the first version) | The visitor can ignore it and keep browsing with the question open. The owner wants a decision before the page is used; the equal Reject all keeps that from being a cookie wall. |
| Record "reject" when the dialog is dismissed or on its own after a time | Recording consent without an interaction is what the documentation forbids. |
| A region prompt for every new visitor, with or without consent | The intrusive pattern 031 warned against; the region row rides on a question that is asked anyway. |
| Making Accept all mean "accept cookies and switch to the chosen country" only | Reject all must confirm the region just as easily, or the region choice would be tied to accepting cookies. Both buttons confirm both. |
| Gate the theme's own preference storage (favorites, color mode) on the answer | Same reasoning as 030: it would disable what the visitor asked for until they answer. |
| Show the dialog to everyone | Shopify's region rules (`shouldShowBanner()`) exist for this; a theme copy would drift. |
| A third-party consent platform | AGENTS.md rule 4, and it would need the same region handling. |

## Edge cases and dead ends

- **Do not use `data-consent` on the root element.** The first version set `data-consent="ready"` on `<html>`, and the click handler matched `closest('[data-consent]')`, which reached the root, so any click inside the dialog recorded Reject all. The root marker is `data-consent-ready` and the handler matches `button[data-consent]`. `scripts/test-consent.mjs` checks that a click on the text or on Preferences records nothing.
- **A modal dialog is dismissed by Escape unless the `cancel` event is stopped:** the first ask prevents it, a reopened dialog allows it. Focus returns to the footer button that reopened it, or to the main content.
- **A modal dialog does not lock page scroll by itself:** `html:has(.consent:modal) { overflow: hidden }` does.
- **`assets/consent.js` imports nothing, on purpose.** Its first version imported `fetchDocument` from `@singi/utils`; on the dev server (`127.0.0.1:9292`) the import map's store-host URL is blocked as cross-origin in a real browser, so the module never ran and the dialog did not show, while every headless test passed (they use `--disable-web-security`). The lazy country list now uses `fetch` and `DOMParser` directly, and `scripts/test-consent.mjs` runs Chrome with web security on. Ten other modules have the same dev-server problem ([architecture.md](../architecture.md#known-issues)).
- **Reviewing it:** add `?consent_preview` to any page address. `assets/consent.js` then shows the dialog with a stand-in API that records nothing (the answers go to the console, the real API is never touched). It works on any store that has the setting on and is harmless on a live one. Without it the dialog shows only when Shopify's API says so, which a store with no consent region never does.
- **`.icon-button` is `display: flex`, which overrides the `hidden` attribute:** the dialog stylesheet sets `.consent [hidden] { display: none }`.
- **Run Shopify's banner and this one together and visitors see two.** The setting's help says to remove Shopify's first; how is not fully documented (see Context), so check a store in a consent region.
- **A visitor who answered in Shopify's banner earlier is not asked again** (`currentVisitorConsent()` has an answer).
- **A region where the API says not to ask** shows no dialog, but the footer button still lets the visitor set choices.
- **The first ask is not dismissible.** There is no close button and Escape does nothing; the page is unusable until an answer is given. If a visitor leaves without one, nothing is recorded and it shows again next time.
- **The region row is the market Shopify resolved, not a suggestion.** The theme has no location data. A visitor whose country belongs to another store of the same business still needs the cross-store suggestion (an unbuilt roadmap item); this dialog does not do that.
- **The localization form is posted after the consent callback** (with a 1.5 second fallback), so the answer is recorded before the page reloads. If recording is slow the region still changes and the consent is asked again on the next page.
- **Shopify's own banner script breaks the dev server for the same reason** (it makes the same Storefront call): turn Shopify's banner off in the admin, or block `/cdn/shopifycloud/privacy-banner/privacy-banner.js` in the browser while developing. The test browsers never load it (`scripts/lib/crawl-sign.mjs`). Found 2026-11-18 ([tooling.md](../tooling.md)).
- **Shopify's copy is on the `unstable` Storefront API version and its query is Shopify's own.** If it changes or fails (a 4xx, a timeout of 2.5 seconds, a missing token) the fallback strings show; the dialog is never held back more than 3 seconds.
- **The suggestion's shape is observed, not documented.** Seen on 2026-11-18: `detected_values.country.handle`, and `suggestions[0].parts.country` and `.language` with `handle`, `options` and `confidence`; the store had no second language yet, so the `language` part was never seen. Treat it as a guess that may change.
- **With a consent region covering the machine, the real API asks in every headless run.** The dev store now has Sweden as a consent region, so with the dialog on the real API asks even without a preview flag, and the modal blocks other tests. `npm run test:all` runs the dialog only in its own last phase; for a single test, `npm run theme:set -- consent_dialog=false --apply` first.
- **A pixel or tag a merchant adds themselves is still not covered** (as in 030): gate it with the Customer Privacy API.
- **`sale_of_data` follows Marketing** as a simple default. Whether a US store needs a separate "do not sell" control is a legal question the theme does not answer.

## Trade-offs we accept

- **The language select and the lazy country list are not tested:** the dev store has two countries and one language, and the dev token has no markets or locales scopes (`read_markets`, `write_markets`, `read_locales`, `write_locales`), so Sweden and Swedish could not be added by script. The code paths exist; the test checks the language select when the store has one.
- **Not verified: a second language on any country.** The dev store's countries (Canada, Sweden, United States) all list only English, so the language select, the suggested language and the Swedish and French copy have only been seen in the stubbed test, not against Shopify. The Storefront copy was seen for English only.
- **Not verified against Shopify's real answer for the dialog's own flow.** The dev store has no consent region and loads no API, so every check runs against a stub that records `setTrackingConsent` calls. Timing, `shouldShowBanner()` in a real region, cookie persistence and the interplay with Shopify's banner are unverified.
- **The theme owns the wording and the layout of a legal control.** The default text is neutral and machine-translated; a merchant is responsible for what it says in their markets.
- **Needs JavaScript and the API.** No JavaScript, no dialog (and nothing non-essential runs).
- **About 4 KB brotli more JavaScript** on every page when the setting is on.

## How to verify

`npm run test:consent` (2 checks with the setting off; with it on, `SINGI_CONSENT=on`, 62 checks against a stub API: shown only when asked, modal (inert page, no scroll, focus on the title and trapped, Escape does nothing, scrim token), nothing recorded before a click, Accept and Reject identical and 44px tall, Accept, Reject and Preferences-then-Save record the right choices, nothing when not asked or already answered, the region row (current country with its currency, the selects, nothing posted when unchanged, the new country posted after consent when changed, no region when reopened), the footer button reopens it (modal, focus back to the button afterwards) with the current choices and Escape records nothing, the `?consent_preview` URL, Shopify's suggestion, copy and the per-country language select (stubbed, in two languages, with the fallbacks), a phone, right to left, dark, no API). `npm run test:all` sets the setting for that run and leaves it on in the dev theme (the shipped default stays off). By hand, on a store in a consent region with Shopify's banner removed: visit with a clean browser, confirm the dialog shows, that no analytics tag fires before a choice, that Accept turns Consent Mode to granted (`dataLayer`), and that Cookie settings reopens it.

## Revisit when

Shopify documents how a theme turns off its banner or reopens its preferences, a store needs a separate "do not sell" control, or the dialog is verified against a real consent region and something differs.
- **Never on a policy page.** The dialog links to the privacy policy, and a modal over that page would make the link useless, so `ready()` does not ask on `/policies/...` (found 2026-11-19). The footer's Cookie settings button still opens it. A visitor who clicks on by soft navigation is asked on the next full page load. The Shopify policy page itself is styled in `assets/policy.css`, inlined by `layout/theme.liquid` on policy pages only (`.shopify-policy__*`, under `main` to win over the stylesheet Shopify loads after the theme's).
- **The region rule and the language select on the dev server.** One rule under the country and language block, with the same space above it as the stack gap below it (`var(--stack)`), and the last button of the card sits one panel padding above the edge, Preferences open or closed. On the dev server choosing another country shows no language select: the languages of a country come from the Storefront API, which the dev server cannot call, and the Liquid `shop.published_locales` does not list the market's languages there either. Review that on the store's preview URL with `?consent_preview`.
- **The privacy link is the theme's own (`shop.privacy_policy.url`), with Shopify's translated link text.** Shopify's `policyLinkUrl` for Swedish is `/sv/policies/privacy-policy`, which is a 404 on a store whose Swedish market lives at `/sv-se` (checked on the dev store 2026-11-19: `/sv/...` 404, `/sv-se/...` 200). The page's own policy URL always exists, so the link never changes with the language chosen in the dialog.
