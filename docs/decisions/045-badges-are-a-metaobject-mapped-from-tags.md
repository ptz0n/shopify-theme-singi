# 045. Badges are a typed metaobject, mapped from product tags, with a built-in "New"

Status: accepted
Area: product card | product page | catalog | content storage | i18n
Code: `snippets/badge-pick.liquid`, `snippets/badge.liquid`, `sections/main-product.liquid` (`.product__badges`), `snippets/product-card.liquid` (`.product-card__badge--custom`), `snippets/tokens.liquid` (`--color-new`), `locales/*.json` (`products.new`), `scripts/lib/badges.mjs`, `scripts/badges.mjs`, `scripts/mock-data.mjs` (`BADGES`), `scripts/test-badges.mjs`

## Context

Sold out and Sale ([decision 044](044-a-sale-badge-from-the-compare-at-price.md)) are the only badges the theme can derive from product data (Sale only from this decision on, and only as an entry). Merchants also want New, Bestseller, Limited, Eco, Gift idea: labels that no field of a product says. The merchant has to be able to choose which products carry which badge and how it looks, without editing the theme and without Liquid that hardcodes tag names. The research for this record (2026-11-18) found that the common practice is one of: a theme's built-in Sale and Sold out only (Dawn); a prefixed tag read by custom Liquid; a product metafield read by custom Liquid; or an app. A metaobject that defines the badge types is the less common hybrid. Shopify's own guidance is to keep metafield and metaobject access out of loops ([move metafield access outside loops](https://shopify.dev/docs/storefronts/themes/best-practices/performance/move-metafield-access-outside-loops)), which a card in a grid is.

## Decision

- **A metaobject definition `badge`** (storefront public read) with four fields: `label` (single line text, required), `color` (color, required, the background), `show_on` (`card`, `product` or `both`; empty means both) and `priority` (integer; the lowest number shows first; empty means 100). The type is the plain, singular `badge`, with no theme prefix: a metaobject is store content that outlives the theme, and the name is what a merchant sees in the admin and what other tools (Flow, apps, imports) would call it ([content-storage.md](../content-storage.md#names-of-metaobject-definitions)). `product_placeholder` ([decision 038](038-placeholder-images-by-type-and-vendor.md)) follows the same rule; it was `singi_placeholder` for a day. The merchant creates entries in the admin (Content > Metaobjects > Badge). The definition's display name is the `label` field, so the admin lists an entry as "New" and not as its handle (`npm run badges -- define --apply` sets it on a definition that already exists, too). `npm run badges -- define --apply` creates the definition on the dev store.
- **A product gets a badge from a tag.** The tag `badge-<handle>` shows the entry with that handle (`badge-bestseller` shows the entry `bestseller`). **The tag `new` and the tag `badge-new` both name the badge `new`.** Tags are matched ignoring case, and one handle shows once however many tags name it. Tags stay the mapping because they are the one product field every import, bulk editor, Flow rule and feed already writes.
- **A built-in "New" works with no entry.** When the handle is `new` and there is no entry with that handle (or it has no label or color), the badge reads "New" (`products.new`, translated in every locale) on a fixed blue (`--color-new`, `#1e4d8c`, white text, 8.6:1). An entry with the handle `new` replaces the label and the color and takes part in priority and `show_on` like any other. No other handle has a built-in: an unknown `badge-<handle>` shows nothing. A plain tag other than `new` (`summer`, `sale`) is never a badge.
- **The text color is derived, not entered.** `snippets/badge.liquid` compares `color_contrast` of the entry's color against white and against black and uses the higher, so no merchant color produces unreadable text and the definition has no second color field. The label is text, so it is read by screen readers and translated with Translate & Adapt.
- **Sale is computed and opt-in.** A product whose compare-at price is above its price (the first variant's, the same rule as before, [decision 044](044-a-sale-badge-from-the-compare-at-price.md)) counts as named by the handle `sale`, with no tag, **but only when a badge entry with the handle `sale` exists** and has a label and a color. With no entry there is no Sale badge: no built-in, no theme setting. The entry's label, color, `show_on` and priority apply like any other entry's, so Sale can show on cards, on the product page or both, and ranks against the tagged badges by priority (an entry with no priority is 100, so it loses to a tagged badge with a lower number; give it a low number to win). A product tagged `badge-sale` or `sale` is just a tagged badge and is not duplicated. The Sale badge on the product page is not a link (it names no tag).
- **On a card, one badge at most, in this order:** Sold out (built in, fixed, card only), then the first badge by priority among Sale (when the entry exists) and the tagged badges that show on cards. The badge sits in the same corner, at the same size and type as Sold out (`.badge-label` joins the shared size and type rule in `base.css` with the Sold out badge and the AI label).
- **On the product page, every badge that shows there sits on the first gallery item, in its top start corner, 12px in, where the card puts its badge**, lowest priority number first, side by side, **two at most** (the two with the lowest priority numbers; a third is not shown, because three or four colored pills over a photo are noise and the order is the merchant's to set). It is rendered by `sections/main-product.liquid` inside the first item (an image, a video or the placeholder), above the zoom button and click-through (`pointer-events: none`), so the image still opens the zoom. It does not depend on availability or price: a sold out product tagged `new` still shows "New". **On the product page, and only there, each badge is a link** to the products with the tag that names it: `/collections/all/<tag>` (`routes.all_products_collection_url`), with `rel="nofollow"` because a tag page is a filtered duplicate of the collection, not a page to rank. The tag is the product's own, handleized: `new` when the product has it, then `badge-new`; a product with both links to `new`. A card's badge stays plain text, because the whole card is one link (decision 001). The link has a 44px target (an invisible extension of the badge) and takes clicks back from the zoom button under it. Nothing renders when no badge matches. On a phone the gallery scrolls sideways, so the badge belongs to the first slide and scrolls away with it.
- **Where a badge shows** is decided before priority: an entry with `show_on` set to `card` is skipped for the page and `product` for the card, then the rest are ordered. So a card-only badge never hides a page badge, and the other way round.
- **No icon, no style choice** (filled, outline, subtle) for now. One filled pill is the one look; the roadmap item listed both as options.
- **Liquid cost.** `badge-pick` is a leaf snippet that loops the product's tags (at most 100) and reads at most four `badge-` tags, each by a lookup by handle (`shop.metaobjects.badge[handle]`), never by iterating the entry list, and only for products that have such a tag. A product without badge tags costs a string comparison per tag. The card renders `badge-pick` and `badge`, both leaves, so no render goes deeper than the card's own image.

## Why

- **Tags are the mapping, a metaobject is the look.** A tag cannot say what color a badge is, whether it is translated or where it shows. A typed definition gives the admin a form for that and keeps the styling in one place for every product that shares it, which is what the research found a metaobject is for.
- **A fallback for the one badge nearly every store wants** means the feature works on a store that has set up nothing, and a store that wants its own color adds one entry. This is the "one good default instead of another setting" rule.
- **Derived text color** removes a field that can only be filled in wrongly.
- **Lookup by handle** is the cheapest way to read a metaobject entry, and doing it only for tagged products keeps the cost proportional to the badges shown.

## Alternatives rejected

| Alternative | Why not |
| --- | --- |
| Theme settings (a list of badge names, colors and tags) | A setting is global and theme-bound: it cannot map a product to a badge, and a merchant's badge definitions would be lost with a theme switch ([content-storage.md](../content-storage.md)). |
| A product metafield (a list of text values) read by the theme | Needs a metafield definition and a column in every import and feed, where tags already work everywhere. It cannot carry color or placement either. |
| A date rule for New (published in the last 14 to 30 days) | Marks whole imports and republished products as new; the merchant decided on a tag (2026-11-17). |
| A built-in Sale, as there is for New (the first version of 044, with a setting) | Sale is implicit: it appears from the price with nothing the merchant did. New needs the merchant to tag a product, so a built-in look is a convenience; Sale would be a surprise on a store that does not want it. Explicit over implicit: the merchant creates the entry, and then chooses its words, color and placement in one place. |
| A theme setting for where Sale shows (off, cards, both) next to the entry | Two places to say the same thing, and the entry's `show_on` already has the vocabulary. |
| A built-in for every common word (Bestseller, Limited, Eco) | Each would need a translation, a color and a default, and most stores want their own. Only `new` is common enough and has no data signal. |
| Treat any plain tag that matches an entry handle as a badge | A tag such as `summer` or `sale` is used for collections, filters and feeds; showing them as badges would be a surprise. Only `new` is special, by name. |
| A text color field (or a style choice) on the entry | A way to get unreadable badges, and more to fill in. |
| Read the whole `shop.metaobjects.badge.values` list once per card | Iterates entries on every card. A lookup by handle reads only the entries a product names. |
| A private product block (a row under the title, the first version) | The badge is a label on the picture, like the card's; a row of colored pills in the details column read as buttons and put the same label in two different places. A block also made the merchant place and keep it, and the gallery cannot take a block. |
| Link a badge to the product's current collection (`/collections/<collection>/<tag>`) | The product page is reached from search, the home page and links with no collection, so the target would change with how the shopper arrived. `/collections/all` is always there and lists every product with the tag. |
| Pass one lookup built once per section into every card | The card is rendered from many sections (collection, search, related, recently viewed, wishlist, the product row) and each would have to build and pass it. Not worth the plumbing before a measurement says the lookups cost anything. |

## Edge cases and dead ends

- **Entry handles are lowercase and the tag is lowercased**, so `Badge-New`, `badge-NEW` and `new` all name the entry `new`. A merchant who changes an entry's handle in the admin breaks the tags that name it (nothing shows, except the built-in `new`).
- **The product page shows at most two badges**, the first two by priority; a product with a third shows two. A card shows one. (Four `badge-` tags are read before that cut.)
- **Only four `badge-` tags are read** (in tag order, which Shopify sorts alphabetically). A product with more than four loses the later ones before priority is applied. A product rarely has more than two.
- **A store that had the Sale badge before this change loses it** until it creates the entry `sale` (the theme is at 0.1.0; `npm run badges -- mock --apply` creates the mock one). The setting "Show a Sale badge" and the string `products.sale` are gone from the theme and the 62 locale files; the label is the entry's, translated with Translate & Adapt.
- **The Sale entry's text color is derived** like any other, so a store that wants the old red uses `#b91c1c` (white text).
- **The built-in New has no priority or `show_on` setting:** it is priority 100 and shows on both. To change that, create an entry with the handle `new`.
- **A new entry can take a few seconds to show** on the storefront (Shopify caches metaobject reads); the same applies to deleting the entry `new` and falling back to the built-in. The test (`npm run test:badges`) does not exercise the built-in for that reason.
- **Do not give a badge the class `.badge`:** it is a bordered variant with other padding (`base.css`), and the badge would stop matching Sold out and Sale. `scripts/test-sale-badge.mjs` and `scripts/test-badges.mjs` compare the metrics of every badge on a card.
- **`new` and `badge-new` link to different lists.** A tag page filters by one tag and cannot combine two with OR, so the badge `new` links to the tag the product has: `new` first when it has both (the owner's rule), otherwise whichever it has. Products tagged only `badge-new` are not in the `new` list, and the other way round. It is up to the merchant to keep the catalog consistent: tag everything one way to get one list.
- **Tag pages are canonical to themselves.** On the dev store `/collections/all/badge-new` printed a canonical link to itself, so a search engine may index it; `nofollow` on the badge links only stops this theme's links from passing weight. Adding a canonical to the unfiltered collection (or `noindex`) on tag pages is not done.
- **A card's badge is not a link** (the card's stretched link, [decision 001](001-stretched-card-link.md), is the one link on the card); only the product page has linked badges.
- **A badge on a product card in list view** uses the same static position as Sold out and Sale (`snippets/view-toggle.liquid`), so list view needed no change.
- **The quick buy dialog and the cart do not show badges**, like the Sale badge. The product page gallery is the one other place.
- **The product page shows no badge when it has no media and no placeholder image** (the first gallery item does not exist). The card has the same limit: it needs an image box.
- **Contrast cannot fall below 4.5:1 by construction.** Whatever the color, the better of white and black has a contrast ratio of at least about 4.6:1 (the worst case is a mid-tone around `#757575`). A merchant who wants a stronger badge picks a lighter or darker color; the theme does not warn about mid-tones.
- **Structured data and the feed are not affected:** badges are presentation. They are not in the JSON-LD.
- If you build a badge from a tag in another snippet, read the tag with `badge-pick`; do not match tags in Liquid again.

## Trade-offs we accept

- **The name `badge` can already be taken.** A store that has its own `badge` definition (an app, an earlier theme, a hand-made one) shares the type with the theme: the theme reads its `label` and `color` fields and nothing else, so entries without them show nothing, but a definition with other field types breaks the lookup. `npm run badges -- define` reports an existing definition that lacks the four fields instead of silently using it. A theme prefix would have avoided the collision at the cost of a worse name in the admin; the owner chose the plain name (2026-11-18).
- A merchant who wants an icon, an outline or a gradient cannot have one.
- Tags carry the mapping, so a typo in a tag shows nothing and no admin screen says so (`npm run badges -- check` lists entries, not tags).
- The Liquid cost of the lookups is not measured against a run without them (see How to verify).

## How to verify

`npm run test:badges` (70 checks on the dev store with the mock entries and tags: one badge per card with Sold out first, then the first by priority of Sale and the tags; `new` and `badge-new` as one badge in the entry's color; priority; card-only and page-only; the product page badges in order, over the first image; contrast of at least 4.5:1 in light and dark; a phone; right to left). `npm run badges -- mock --apply` creates the entries and tags the mock products first (`npm run test:all` does it).

The built-in "New" was checked by hand on 2026-11-18: with the entry `new` deleted, the card and the product page showed "New" on `rgb(30, 77, 140)` with white text; after recreating the entry they showed `rgb(47, 111, 79)`.

Liquid time: `npm run perf:liquid -- --url /collections/mock-edge-cases --runs 5` on the dev store gave 39 ms for the whole render and about 12 ms for `snippets/product-card` with four of the page's cards carrying a badge tag. `badge-pick` and `badge` did not appear among the profile's files (their time is part of the card's). No run without the badge code was taken, so the cost they add is **not measured**.

## Revisit when

The Liquid cost is measured and is more than a card can afford, or a merchant needs an icon or another look (add a `style` field and an optional icon file field to the definition), or Sold out should become an entry too so its look can be changed (Sale already is one).

Sale has its own test, `npm run test:sale-badge` (17 checks with the mock `sale` entry: the card, the product page with Sale first, red on white; and 7 more with the entry deleted, which `npm run test:all` does for one run and then restores). Checked by hand on 2026-11-18: with the entry deleted no card or product page showed Sale, and after `npm run badges -- mock --apply` both did.
